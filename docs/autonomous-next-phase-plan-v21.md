## 1. 検証済みの2万分類版をmainへ反映する

文書とPRの件数・CI結果を揃え、公開する差分とcommit情報を確認する。CI対象`b4464aa`以降が文書だけであることを確かめ、実装・試験・依存・workflowが変わっていなければ同じCIを追加しない。既存のマージ許可の範囲でPRを確定・反映し、mainとリモートの一致を確認する。

**完了条件:** 2万分類版の実装・結果文書がmainへ反映され、採用したCI対象との対応とGitの保存先が分かること。実DB・原資料・個人履歴は引き続きGit対象外とする。

## 2. 本当に未処理の資料を一度棚卸しする

保存済み台帳・原資料・予約・失敗・保留を照合し、既存2万作品と過去の試行を除く。未処理資料の在庫が追加1万作品分あるとは仮定しない。日本語、現代ミステリー、ファンタジー、ライトノベル、年代・国の不足を優先し、根拠のある区分別に投入可能数と不足を記録する。書誌ジャンル不明を推定ジャンルの件数に混ぜない。

既存2万作品の比較用ID・行digestと、新規入力のID・hash・資料版・用途条件・作品対応を固定し、出力先を分ける。全DBの複製や既存分類の再実行は行わない。資料不足に対する追加経路の適合性調査は最大2経路・各1回とし、新しい根拠なしに同じ低収率の取得・調査を繰り返さない。

**移行条件:** 投入可能な新規資料数、優先順位、不足区分、非重複の入力と反映先が確定していること。全区分の資料が揃うまで成立済み区分を待たせない。

## 3. 成立した資料から累計3万作品へ追加する

既存の分類・別審査・用途確認・DB採用を再利用する。Sol CLIは既存の4/8並列制御、最大8並列を維持する。分類は1作品/呼出し、別審査は既存の最大5作品/呼出しとし、資料準備など独立する処理を並行する。DB書込みは一系統とし、採用できた区間から推薦に反映する。

失敗率5%以下・表示特徴採用率70%以上の条件を緩和しない。同じ失敗入力を自動再送せず、停止・保留は正常区間と別に保存する。引用・資料版・作品ID・入力hash・用途条件・採用ラベルを対応させ、根拠がない属性は不明とする。

**完了条件:** 既存20,000分類を保持し、新規採用10,000作品を加えて実DBで30,000作品になること。追加分の監査、6軸・不明・言語・年代・国の内訳、実時間とCLI利用量、推薦動作を確認する。投入数と採用数を混同せず、届かなければ到達数と不足を報告する。

## 4. 3万から5万、10万作品以上へ進む

3万作品までの実際の供給量・採用率・処理時間から、5万、10万作品以上の差分入力と見通しを決める。各段階の移行条件は、前段階の保持、新規採用分の根拠・用途条件・監査、推薦動作の確認である。検索可能な約10万作品と、詳細分類10万作品は別目標として扱う。

独立評価の未成立や全ジャンルの資料不足を、成立済み作品の利用・拡張を止める条件にしない。既存335評価は新しい作品対応の根拠が得られた対象だけ照合する。評価母数が成立した場合に限り同じ対象で推薦を比較し、作品・翻訳・著者・シリーズの漏洩を確認する。全件再照合や独立正解の探索を反復しない。

## 5. 用途条件を満たす範囲でToC提供を具体化する

[ToC候補](toc-candidate-v1.md)を基に、AI入力・表示・再配布・商用の条件を資料と用途ごとに確認する。コードと依存物の配布条件、出典表示、履歴の保存・削除・持ち出し、無料運用可能な公開構成を具体化する。現在はローカル試作で、一般公開・商用提供は未実施である。

**移行条件:** 配布するコード・データ・出典と用途条件、個人データの扱い、実際の公開構成が成立していること。追加費用・外注・本人の追加採点を前提にしない。

## 実行と検証の上限
