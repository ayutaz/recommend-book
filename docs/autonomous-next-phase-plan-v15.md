## ここからの順序

1. 今回の成果を検証・Git反映まで終える。画面、実採用数、原物との対応、必要な試験と最終版CIを確認する。文書更新だけでモデル・DB生成・全件試験を繰り返さない。
2. 履歴接続や分類根拠の不足を解消できる、新しい無料資料の経路に絞る。用途条件と原作品・翻訳・シリーズ・刊行版の対応を確認してから使う。既に不成立と確認した経路を新根拠なしに再探索しない。
3. 新しい接続が増えた場合だけ、データ版・比較仕様・分割を固定して推薦を再評価する。独立注釈が適合するラベルだけ分類精度を測り、不足範囲は未評価にする。無料資料で解決できない不足は理由を記録して止める。
4. 品質・対象構成・採用率・速度・利用枠が整った段階で、1万→3万→10万作品へ拡張する。候補数だけで次へ進めない。

分類はCodex Sol CLIで最大5作品/call・2並列を基本とする。並列数は時間・失敗率・枠の実測で必要な場合だけ増やす。採用率70%以上、出力検証保留5%以下を運用目標とし、精度指標と混同しない。新しい根拠がある対象だけを小バッチで処理し、同一入力の無変更再試行をしない。

## 守る条件

- 外注・購入・有料API・見積照会を行わない。本人の試読・採点・正解作成・履歴入力・画面確認を必須にしない。追加本人評価なしでは本人満足度の実測を保証できない。
- 取得、保存、外部AI入力、画面表示、再配布、商用利用を資料・項目・用途ごとに確認する。取得できることを利用許可と扱わない。新規取得時にはその時点の公式条件を確認する。
- 原記録・作品・原文/翻訳表現・刊行版・シリーズ・派生関係を分ける。タイトルやISBNだけで統合しない。疑わしい対応は保留し、訂正を取り消せる履歴を残す。
- 6軸の分類には根拠と対象表現、present/absent/unknown、関連度、未校正confidence、処理版を保存する。原文と翻訳の文体を分け、unknownを負例へ変換しない。未校正の値を好みに合う確率と扱わない。
- 新規・変更・撤回だけを処理する。入力・原応答・終了状態・利用量・採用理由を残す。同じ比較、全DB生成、同じ大きな実行ファイルのhashを目的なく繰り返さない。
- 元履歴・個別評点・原文引用・DBはローカルdata/に保持しGitや画面へ含めない。再配布できる部分と再取得手順を区別する。
- GitはブランチとPRを使い、自動commit・push、最終版CI確認後の許可済みマージを行う。mainへ直接pushしない。

通常の実装・検証・Git反映で確認は求めない。本番公開、許可範囲を超える私有履歴利用、品質目標の変更が必要になった場合だけ、具体的な成果物と選択肢を示してユーザーへ判断を依頼する。現在、回答待ちの質問はない。

納期は実採用数・保留率・全工程時間から見積もる。履歴接続と独立正解の確保が不確定なため、10万作品と本人向け改善までの確定日は置かない。進捗は文書数や呼出回数ではなく、採用作品数・接続数・評価範囲・更新検証で報告する。
