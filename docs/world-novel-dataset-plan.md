## 目的と対象範囲

世界の小説を作品単位で統合し、推薦に利用できる根拠付きの多ラベル分類データを構築する。今回の対象は、1 書誌・作品情報の収集、2 名寄せと作品DB、3 LLM分類、4 関連度・信頼度の付与と分類精度の検証までとする。推薦精度の検証は次の段階で行う。

LLM処理は、CodexのSolを非対話CLIから実行する。ローカルのモデル一覧で確認できた `gpt-6.1-sol` を初期設定とし、モデルIDと実行設定を固定・記録する。Pythonのスケジューラが複数のCLIプロセスを管理する。CLIから利用する既存認証と、その利用枠・制限を前提にし、API課金単価から費用を断定しない。

PoCはまず1,000作品を成立させ、目標2,000作品、最大3,000作品まで拡張する。その後1万〜3万作品、最終的に10万作品以上へ進める。件数はISBN数や取得レコード数ではなく、統合後の異なる作品数で数える。書誌のみの作品と、分類根拠が揃った作品の件数を別に報告する。

以下のDB構成、件数配分、並列度、精度閾値は設計提案であり、達成済みの性能ではない。100作品の試行で調整し、最終評価に使う前に固定する。

## 作成時点（2026年10月12日）の現状と設計への影響

ローカルの `CLAUDE.md` と `scripts/` には、日本語エンタメ系書籍の調査資料と、NDL、openBD、なろう、AniList、Jikan向けの収集スクリプトがある。Open Library・Wikidataの収集器、統合DB、分類器、評価基盤、Pythonの依存管理設定は、今回確認したファイルにはない。

`scripts/collect_ndl_full.py` の `deduplicate()` は、ISBNがあればISBN、なければタイトルと著者で取得レコードを重複除去する。これは原題・翻訳・異なる版を作品単位へ統合する機構とは別である。`extract_record()` はタイトル・著者・出版情報などを抽出するが、提供機関IDと項目ごとの利用条件を統合DBに引き継ぐ設計を追加する必要がある。

`scripts/collect_openbd_full.py` のISBN正規化・変換、あらすじ・寄与者・シリーズ情報の抽出処理は再利用候補とする。ただし、ISBNチェックディジットの検証、寄与者の役割、原データ保存、再開処理は新しい入力仕様に合わせて検証する。既存の検索語や収録率の観測結果を世界の小説全体に一般化しない。

## 1 書誌と作品情報の収集

### データソースの役割と利用条件

| ソース | 主な役割 | 取得方法の計画 | 利用条件の扱い |
|---|---|---|---|
| Open Library | 海外の作品・版・著者・別題・主題情報 | 月次のworks・authors・editionsダンプを必要範囲で抽出。APIは少量の動作確認・個別照会に限定 | 権利が一律に解消されたデータとは扱わず、説明文・画像などを別審査 |
| NDLサーチ | 日本の刊行物、日本語訳、ISBN、著者・訳者・シリーズ情報 | 許可した提供機関に限定した検索用API。まとまった初期取得・更新はPoCからOAI-PMHを検討 | 提供機関と項目の条件、表示すべき出典を保存 |
| Wikidata | 作品・著者ID、原言語、刊行情報、原題と翻訳の対応候補 | 範囲を限定したSPARQL・エンティティ取得。拡張時はダンプ抽出を比較 | 構造化データのCC0と、リンク先の本文・画像の権利を分離 |
| openBDなど既存ソース | 日本語書誌・あらすじ・ライトノベル情報の補完候補 | 現行条件を再確認してから追加 | 既存資料の「無料」「認証不要」を利用許諾の代わりにしない |

Open Libraryの公式案内では、APIによる大量メタデータ取得を避け、月次ダンプを利用するよう求めている。APIを商用サービスの大量アクセス基盤にすることも想定されていない。PoCからダンプを中心にする。既定のAPI制限は未識別1 req/s、連絡先付きの識別済みリクエスト3 req/sだが、これは大量収集の許可ではない。[Open Library API方針](https://openlibrary.org/developers/api)、[月次ダンプ](https://openlibrary.org/developers/dumps)

Open Libraryのライセンス案内は、Internet Archiveが追加の権利を主張しない一方、投稿内容や法域によって既存の権利問題があると明記している。あらすじ・表紙・本文の商用利用や外部LLM入力を一括許諾と解釈しない。[Open Library Licensing](https://openlibrary.org/developers/licensing)

NDLサーチは営利・非営利の目的と提供機関に応じて申請・許諾条件が異なる。`open` はPDMまたはCC0のメタデータを横断取得するための指定であり、NDL提供データすべてを意味しない。表に掲載される二次利用条件はメタデータの条件で、コンテンツの条件は別途確認が必要である。多重アクセスを避け、NDL向けの通信は全ワーカー共通で1リクエストずつにする。[NDL API利用案内](https://ndlsearch.ndl.go.jp/help/api)、[提供機関と利用条件](https://ndlsearch.ndl.go.jp/help/api/provider)

Wikidataの構造化データはCC0で公開される。Wikipedia記事、Wikisourceの本文、外部画像などへ同じ条件を自動適用しない。[Wikidata Licensing](https://www.wikidata.org/wiki/Wikidata:Licensing)

NDLの2026年9月25日版仕様では、SRU・OpenSearchの検索結果は最大500件の範囲に制限され、開始位置を指定しても501件目以降は取得できない。検索結果の打切りを全件取得成功として扱わない。検索用APIは同定後、OAI-PMHは各提供機関の同定前メタデータを対象にするため、提供元の追跡にも差がある。大量取得は対応する提供機関のOAI-PMHを基本に検討し、継続トークンと更新日時を保存する。[NDL外部提供インタフェース仕様 第1.5版](https://ndlsearch.ndl.go.jp/file/help/api/specifications/ndlsearch_api_20260925.pdf)

分類用の文章は、名称だけで同じ意味と見なさない。Wikidataの `description` は項目を区別するための短い説明で、あらすじではない。[Wikidata Description](https://www.wikidata.org/wiki/Help:Description)。NDLでは `dcterms:abstract` が要約等、`dcterms:description` が注記であり、要約の存在や利用可能性を保証しない。[DC-NDL v3](https://ndlsearch.ndl.go.jp/renkei/dcndl/version3)。説明文の種類と由来を正規化後も保持する。

利用条件台帳は、ソース・提供機関・データ種別・項目単位で、取得、ローカル保存、外部LLM入力、商用利用、表示、再配布、帰属表示、保持条件を記録する。各用途を `allowed / conditional / denied / unresolved` で管理し、根拠URL、確認日、適用範囲を持つ。記載のない許諾を推定で `allowed` にしない。未解決の文章はLLM入力へ送らず、利用可能な書誌情報と区別する。

### 収集工程

1. 既存の取得器と過去の出力形式を棚卸しし、標準レコード仕様と保存ルールを決める。
2. 各ソースを少量で確認する。応答形式、外部ID、言語、説明文、欠損、利用条件が抽出できるかを調べる。
3. ダンプは実際のサイズ・空き容量・処理時間を確認し、works・authorsから抽出、必要に応じてeditionsを追加する。月・URL・チェックサム・抽出条件を記録する。
4. 原データを保存できるものは変更せず保存し、正規化データを別に生成する。保存禁止・保持条件がある場合はその条件に従う。
5. 取得ID、提供機関、取得時刻、入力ハッシュ、出典URL、利用条件IDを付ける。重複応答を破棄して出典を失う構造にしない。
6. 書誌の欠損と分類用根拠の欠損を別に計測し、根拠不足の作品も欠損評価用のサンプルとして残す。

PoCの層は、原言語、作者・作品に紐付く地域、原作品の初出年代、ジャンル、資料の充実度で作る。年代は1900年より前、1900〜1949年、1950〜1999年、2000年以降を初期区分とする。地域と国籍、舞台、原言語を混同しない。複数地域や不明値を許容する。

初期配分の目安は日本語原作35%、英語原作35%、その他の原言語30%。非英語の欧州、東アジア・南アジア、中南米、アフリカ・中東などの不足を明示して補う。これは世界の小説母集団を統計的に代表する比率ではなく、PoCの偏りを検出するための配分である。人気作品だけ、あらすじが豊富な作品だけを採用しない。

**成果物**はソース・利用条件台帳、取得スナップショット、標準化レコード、候補作品一覧、欠損と分布のレポート。**完了条件**は、採用レコードの出典・利用条件参照が100%存在し、再実行で不要な重複が増えず、予定した層ごとの不足を説明できることとする。

## 2 名寄せと作品単位のDB

### データモデル

| 主なエンティティ | 保存する内容 |
|---|---|
| `works` | 内部作品ID、作品種別、代表題、原題候補、原言語、初出情報 |
| `agents` と `contributions` | 著者・訳者・編者などの同定IDと役割 |
| `expressions` | 原文、翻訳、改訂・抄訳などの表現。訳者、言語、対象文体の範囲 |
| `editions` | 出版社、刊行日、版表示、文庫・電子書籍など。ISBNはここに紐付ける |
| `edition_contents` | 版と収録作品・表現の関係。合本・短編集の複数作品を保持 |
| `series` と `work_relations` | シリーズ所属、順序、収録、翻案・関連作品などの型付き関係 |
| `titles` と `external_ids` | 別題、言語、文字体系、原題・翻訳題などの種別、外部ID |
| `source_records` と `field_assertions` | 原レコードと各項目の値、出典、矛盾、取得履歴、利用条件 |
| `resolution_decisions` | 同一作品候補、判断根拠、審査結果、統合・分割・取消履歴 |

一つの作品に複数の翻訳表現と出版版が対応する。短編集・合本の一つの版が複数の作品を収録する関係も表現する。シリーズ名や登場人物名から各巻を同じ作品に統合しない。短編単体と短編集全体を区別し、再編集された短編集を収録作品の一致だけで統合しない。

原作の初出年と翻訳版・再刊版の刊行年を分離する。初出が雑誌掲載・連載・単行本のどれかも記録し、不確実な年は精度や範囲を保持する。翻案、漫画化、児童向け再話は型付きの関係を付け、原作との同一性を自動確定しない。

Open Libraryの検索結果は作品情報と版情報を含み、作品の下に複数言語の版が存在する。一方、外部の作品IDもそのまま正解とせず、外部IDの種別・対応根拠を保持する。[Open Library Search API](https://openlibrary.org/dev/docs/api/search)。Wikidataの書籍モデルも作品と版を区別するため、対応候補の基礎に利用する。[Wikidata WikiProject Books](https://www.wikidata.org/wiki/Wikidata:WikiProject_Books)

### 名寄せ工程

1. Unicode・空白・記号・ISBNを正規化する。ただし、巻番号・副題・原綴りなどを消して元情報を失わない。ISBNはチェックディジットも検証する。
2. 著者の外部IDと異表記を同定する。同姓同名、共同著者、筆名は保留可能にする。
3. 外部の作品IDや明示的な翻訳・版の関係を強い候補に使う。ISBN一致は出版版の候補であり、それだけで複数の収録作品を一つにしない。
4. 著者・別題・原言語・初出・巻次などで候補を絞り、複数の一致と矛盾を評価する。タイトル類似だけでは作品を自動統合しない。
5. Solには難しい候補の証拠整理と `same / different / uncertain` の提案を担当させる。根拠のない原題対応を生成して確定しない。
6. 自動確定・人手確認・別作品・保留を分ける。統合前のIDと原レコードを保持し、取消・分割を可能にする。名寄せの確率と分類の信頼度を別管理する。

PoCの正解には、同一作品と別作品の候補ペアを計300〜500組用意する。原題と翻訳、異なる訳者、文庫化、同名異作品、巻違い、短編と短編集、改作を含める。無関係なペアだけで高精度に見せない。候補探索の再現率、統合判定の精度・再現率、クラスタ内の誤統合を評価する。

**成果物**はSQLiteの作品DB、統合・審査履歴、外部ID対応表、正解ペアと評価結果。**暫定目標**は自動統合のprecision 99%以上とするが、標本数と95%信頼区間を併記し、件数不足の対応種類は品質保証の対象に含めない。**完了条件**は1,000以上の作品IDと版・出典の関係を保持し、誤統合の取消試験と同名異作品の非統合試験が成功することとする。

## 3 Solによる多ラベル分類

### 分類体系と判定の範囲

| 分類軸 | ラベルの例 | 主な判定範囲 |
|---|---|---|
| ジャンル | ミステリー、ファンタジー、SF、恋愛、歴史、ホラー、文学 | 作品。ライトノベルなど出版上の区分は別項目にも保持 |
| テーマ | 復讐、成長、家族、喪失、階級、倫理、移民 | 作品 |
| 物語構造 | 謎解き、旅、複数視点、非線形、群像 | 根拠が揃った作品または表現 |
| 主人公 | 探偵、学生、子ども、人外、複数主人公 | 明示された役割・属性。推測できない属性は不明 |
| 文体 | 簡潔、叙情的、口語的、実験的、心理描写中心 | 原文または指定した翻訳表現 |
| 雰囲気 | 緊張感、陰鬱、温かい、ユーモラス、切ない | 作品または特定の表現。根拠の範囲を保存 |

v1は6軸・総計60〜100ラベル程度を目安に定義する。安定したラベルID、定義、包含・除外条件、具体例、階層、相互矛盾の規則を持つ。物語構造には展開と語りの構造を区別する下位区分を設ける。単なる舞台属性や作品の国籍と、テーマを混同しない。

初期には検証可能な20〜30の主要ラベルを品質ゲート対象とし、残りは探索的なラベルとして支持件数と不確実性を報告する。モデルの自由生成タグは候補として保存し、正式ラベルへ自動追加しない。作品数に対して細かすぎる体系は、分類結果の見た目を増やしても品質検証が成立しないため、PoCで見直す。

### 根拠と出力

LLM入力は、名寄せ済み作品ID、版・表現ID、利用可能な書誌、既存の主題、許諾を確認したあらすじ・本文抜粋等から作る。入力資料は指示ではなくデータとして扱う。作品名についてのモデルの記憶だけを分類根拠にしない。

出力には以下を含める。

- 作品ID、表現ID、対象言語、分類体系・プロンプト・モデル・CLIバージョン。
- ラベルID、判定 `present / absent / unknown`、判定が適用される範囲。
- 関連度、未校正のモデル信頼度、校正後の信頼度と校正バージョン。
- 根拠資料ID、箇所、必要最小限の引用または要約、根拠の直接性。
- 不足理由、資料間の矛盾、ネタバレ区分、人手確認の要否。

関連度は特徴の中心性を0〜1で表し、0.25は周辺的、0.5は明確な要素、0.75は主要、1は中核という初期基準を置く。根拠不足なら `null` とし、単に記述がないことを関連度0や否定へ変換しない。否定を確定するにも十分な資料を必要とする。

信頼度はその判定の正しさに関する値とし、関連度と混ぜない。モデルの数値は未校正値として保存する。校正に必要な人手データが不足するラベル・言語・資料種別では、校正済み確率を表示せず `uncalibrated` と明示する。複数のSolの一致率も正しさの確率に置き換えない。

あらすじだけでは原文の文体や終盤の構造を判断できないことがある。その場合は `unknown` にし、原文と翻訳の文体を分ける。結末・叙述トリックなどのラベルはネタバレ性を保持し、将来の表示で制御できるようにする。

### 並列CLIの実行基盤

Codex CLIは `exec` の非対話実行、`--json` のイベント出力、`--output-schema` の構造化最終出力、`--output-last-message` の保存に対応する。スキーマによる制約に加えて、アプリ側でも検証する。[OpenAI公式の非対話実行ガイド](https://learn.chatgpt.com/docs/non-interactive-mode)

予定する実行形は次のとおり。PowerShellの引用・文字コード、CLIの起動方法、出力スキーマ対応は実装時に少量で確認する。

```text
codex exec --model gpt-6.1-sol --sandbox read-only --ephemeral
  -c model_reasoning_effort=medium --json
  --output-schema schemas/classification.schema.json
  --output-last-message <jobごとの結果ファイル> -
```

プロンプトと入力JSONは標準入力で渡す。Pythonではシェルの文字列展開を介さず、引数配列と標準入力で実行する。Windowsでは確認した実行ファイル・Nodeエントリを使い、CLIの終了コード、タイムアウト、標準出力・標準エラーを管理する。分類ワーカーは承認済みのローカル入力だけを使用し、Web検索やデータ再収集、追加サブエージェント生成を行わない構成にする。

| 制御項目 | 初期設計 |
|---|---|
| 処理単位 | 初期は1作品1ジョブ。起動コストが大きければ、試行後に5〜10作品の小バッチと比較 |
| 並列度 | 2から開始し、4、8を比較。最適値は実測で選択 |
| 成功の扱い | 終了コード0に加え、JSON Schema・ID・ラベル・根拠参照が有効なものを成功とする |
| 重複防止 | 作品・表現ID、入力ハッシュ、taxonomy、prompt、model、設定の組で冪等キーを作る |
| 再開 | ジョブの状態、リース期限、試行回数を保存し、完了済みは再利用 |
| DB書き込み | ワーカーは個別結果へ出力し、検証後に単一の書き込み担当がSQLiteへ反映 |
| 失敗 | 一時的な制限・通信障害はジッター付きバックオフ。意味的不備と構文不備を分け、最大3試行で保留 |
| 利用上限 | 観測できる利用量、実費、実行時間、同時実行数に上限を持つ。制限時は投入停止・再開可能にする |
| 再審査 | 低信頼、根拠矛盾、名寄せ疑義を別ジョブで確認。通常全件を複数回分類する方式は避ける |

100作品の固定試行セットで処理速度、p50/p95時間、JSON失敗率、制限・再試行率、根拠の誤参照率、端末資源を測る。同じ100作品を並列度2・4・8で全部再実行すれば計300作品処理となる。基準結果はキャッシュする一方、性能比較は別runとして意図的に再実行し、追加の利用量を見積もる。

並列度を上げたときの処理量増加15%以上、失敗率2%以下、p95悪化25%以内を初期の選択目安とする。待機時間が増える場合は並列度を半減する。収集APIの制限はこの並列度から独立した全プロセス共通の制御にする。

全体の所要時間は100作品の実測から推定する。概算は「作品数 × 平均処理秒 ÷ 同時実行数」に、再試行・待機・検証・人手確認を加える。10万作品で同じ速度が維持されるとは仮定しない。

**成果物**はtaxonomy v1、プロンプト、出力Schema、CLIジョブ実行器、作品ごとの分類と根拠、利用量・速度のレポート。**完了条件**は1,000作品以上について有効な結果または明示的な保留理由が保存され、中断から再開して二重反映が生じないこととする。

## 4 分類精度と信頼度の検証

### 人手の正解データ

基本セットは400作品とし、開発150、校正100、最終評価150に分ける。PoC全体の原言語・年代・ジャンル・資料量・翻訳有無を層化し、希少ラベルや難例は別の追加セットで評価する。全体分布を反映するセットと難例を過剰抽出するセットを混ぜて、全体精度を計算しない。

同じ作品・翻訳・近縁版は分割をまたがせない。著者・シリーズをグループ化して分割し、偏りが大きい場合はその偏りと評価可能範囲を記録する。最終評価セットを見ながらラベル定義・閾値・プロンプトを修正しない。修正する場合は新たな評価版として、未使用の評価セットを用意する。

2名の独立した人手判定と、不一致の裁定を基本とする。人手リソースが1名の場合はその制約と一部の時間を空けた再判定を記録し、独立2名の検証と同じ保証を主張しない。正解ラベルの根拠、関連度、判定可能性、ネタバレ性も記録する。

人手の実施量は最初の20作品で測る。仮に入力資料に対する判定が1作品1名あたり5〜15分なら、400作品を2名が判定するだけで約67〜200人時を要する。これは見積もりの仮定であり、裁定や作品を読む時間を含まない。人手の人数が少ない場合は、まず100作品・主要ラベルに評価範囲を縮めて結果を出し、400作品へ段階拡張する。評価が済んでいないラベルへ品質保証を広げない。

評価は二つに分ける。

1. **入力資料に対する忠実性**：LLMが受け取った資料から、そのラベルを判定できるか。全400作品で実施する。
2. **作品内容に対する正しさ**：作品を理解した人手または利用可能な十分な資料に照らして、作品の特徴として正しいか。まず50〜100作品の詳しい評価セットを作る。

短いあらすじだけを人手とLLMが共有して一致しても、作品の文体・構造が正しいと確定したことにはならない。作品内容の検証が不足する軸は、入力資料に対する精度だけを報告する。同じSolによる再分類は、疑義の発見に使い、人手正解データの代用にしない。

### 評価指標と校正

| 対象 | 主な指標 |
|---|---|
| 分類 | 軸別・ラベル別precision、recall、F1、micro F1、macro F1、支持件数 |
| 関連度 | 人手の段階評価との平均絶対誤差・順位相関・不一致事例 |
| 信頼度 | calibration曲線、Brier score、ECE、信頼度帯別の実精度 |
| 判定範囲 | 根拠の充実度、評価可能率、保留率、採用率、精度とcoverageの関係 |
| 根拠 | 存在しない資料・箇所の参照、引用の不一致、資料から支持されないラベル |
| 偏り | 原言語、地域、年代、ジャンル、翻訳、資料種別ごとの性能 |
| 運用 | スキーマ有効率、最終失敗率、再試行率、実測速度、利用量、人手確認時間 |

`unknown` を負例として扱わない。人手が判定可能な項目でモデルが保留した場合は、precisionだけで除外せず、正例の未検出と判定coverageに反映する。人手でも判断できない項目は正誤評価から分離し、不適切な断定率を測る。高信頼ラベルだけ採用して精度が上がる場合も、採用率を必ず併記する。

信頼度の校正方式は、校正セットの規模に応じた帯別実精度やシンプルな校正を先に比較する。データが少ないラベルに複雑な校正器を作らない。モデル変更、プロンプト変更、入力資料の変更時には校正の有効範囲を確認し、必要なら再校正する。

95%信頼区間を添え、分類性能は著者・シリーズのグループを考慮した再標本化、割合は標本設計に合った区間を用いる。主要ラベルでも正例が少ない場合は追加評価を行う。400作品ですべての国・言語・100ラベルを同程度に保証することは目標にしない。

### PoCの暫定品質目標

以下は100作品試行後に凍結する仮目標である。達成できない軸・ラベルは保留・探索扱いにして、達成済みと報告しない。

| 項目 | 仮目標と判定方法 |
|---|---|
| 構造 | 再試行後の有効JSON 99%以上。DBに採用する結果はすべてSchemaと参照検証を通す |
| 根拠 | 採用ラベルに根拠IDが100%存在。人手監査で架空・誤参照の比率1%以下を目標とし区間を付ける |
| 主要ラベル | micro F1 0.80以上、macro F1 0.65以上を初期目標。対象ラベル・支持件数と全ラベルの結果を併記 |
| ラベル別 | 主要ラベルprecision 0.85以上、recall 0.65以上を目標。最終評価で正例20件未満は確証不足として扱う |
| 高信頼の採用 | 実precision 0.95以上を目標とし、点推定・区間・採用率を報告 |
| 校正 | 十分な評価標本のある範囲でECE 0.10以下を目標。範囲外は未校正とする |
| 判定coverage | 利用可能な根拠がある作品で、ジャンル・テーマの判定coverage 80%以上を初期目標。全登録作品に対する率も別掲 |
| 文体・構造 | 作品内容の正解と十分な入力がある範囲で評価。資料不足の作品へ目標coverageを強制しない |
| 再現・復旧 | 固定入力で実行履歴を追跡でき、強制中断・再開・再投入後のDB整合性試験が成功 |

PoCの完了は、評価を実施して品質と限界を示せることを意味する。全精度目標の達成や、商用サービスへの投入可否とは別に判断する。機械的に分類が完了した件数だけで品質達成としない。

## 実装構成と検証方法

初期案はPython、uv管理、SQLiteとファイル保存、JSON Schemaの構成とする。SQLiteは統合とジョブ状態の管理に使い、書き込みを一箇所へ集約する。大量ダンプはストリーミング処理を基本にし、必要ならParquet等の分析用出力を追加する。PostgreSQLへの移行は10万作品という件数だけで決めず、同時書き込み・運用要件を測って判断する。

予定する配置は `src/recommend_book/` にingestion、normalization、resolution、classification、evaluation、jobs、`schemas/` に入出力仕様、`config/` にソース・分類体系設定、`tests/` に重要な不変条件のテストを置く。`data/raw/`、`data/processed/`、`data/runs/`、`data/evaluation/` は既存の `data/` 除外方針に従う。配布用データは利用条件が成立するものだけを分離して生成する。

依存関係は `uv add` と `uv add --dev` で管理する。ISBN検証、巻次を失わない正規化、作品・表現・版の関係、短編集、非統合事例、原データと出典の保持、LLM出力検証、リース失効・再開をTDDで実装する。ネットワークとLLM呼び出しを固定fixtureで置き換えたテストをCIで実施し、ライブ収集・大量分類は明示的なCLIジョブで実行する。評価データ自体を実装に都合よく作り替えない。
