入力準備と並行して分類を開始した。書誌ジャンル不明作品の最初の83作品は4並列で処理し、分類82作品・DB採用81作品・表示特徴71作品・内容根拠付き非ジャンル特徴65作品となった。分類失敗1作品と用途確認による未採用1作品は保持し、再送しない。実際の分類・別審査・利用条件確認・DB反映を経てcontrollerはexit 0で終了し、後続へ移行した。書誌ジャンル不明と資料ジャンル推薦の対象外という元の書誌情報は変更せず、本文から採用した特徴を別に使う。後続は既存の4〜8並列制御を維持する。2万分類への拡張に不要な一般書誌の追加収集は後回しにする。

既存制御では分類失敗があった区間の次は4並列となり、条件を満たす正常区間の次は8並列へ戻る。停止直前は8並列だった。再開は既存制御の初回4並列とし、正常区間の結果に基づいて最大8並列へ戻す。以前に確認した3区間の失敗理由は、入力hashの不一致2件と、資料に存在しない根拠引用1件だった。これらの出力は保留を維持し、再送や採用条件の変更は行っていない。

失敗率5%以下・表示特徴の採用70%以上という既存条件を維持する。日本語、ミステリー、ファンタジー、ライトノベル、年代の不足を優先するが、実資料の在庫がある範囲とする。国・地域と根拠のない文体は推測で補わない。

**完了条件:** 既存10,000作品を保持し、新規採用10,000作品を加えた20,000作品が実DBにあること。資料不足で未達の場合は到達数と不足を記録し、達成とはしない。表示特徴・6軸の採用と保留・偏り・実時間・CLI報告の利用量を併記する。

### 3. 待ち時間と履歴管理を並行して仕上げる

重複JSON処理の削減と証跡照合の最大4並列化を実装した。同条件・分類10,000作品の実HTTP各1回では、約42.9秒から約22.4秒となり、推薦30件の公開レスポンス全体が一致した。JSON処理の削減だけの段階では改善を確認できず、その後の証跡照合の並列化を含めた測定である。関連56試験が通過し、内容の二重読取り・改竄検出・撤回検出と、リクエストをまたいだ検証の再利用禁止を維持する。全件の証跡照合や性能調査の反復で分類拡張を止めない。

読書状態の保存・再起動・JSON持ち出し・削除は実装・確認済みである。削除と競合更新の試験には合成データを使い、本人の履歴は削除しない。今回の持ち出し・削除対象は読書状態であり、既存335評価やすべての設定ではない。

再起動は実際のサーバープロセスを終了して別プロセスで起動し、合成3件の状態とexportが一致することを確認した。実ブラウザーからの保存では、新しく作成されたJSONファイルを読み取り、スキーマ・チェックサム・実HTTPとの内容一致を確認した。この時点の実際の読書状態は0件であり、複数件の状態・削除・競合更新は合成データで検証している。

### 4. 差分評価と利用準備をまとめ、Gitへ反映する

新しく確実な作品対応が得られた既存評価だけを照合する。比較可能な母数が成立すれば、資料ジャンルだけの推薦と内容特徴を使った推薦を同条件で比較する。成立しなければ評価不能と記録し、追加の本人評価や有料の評価資料は求めない。

最終監査・既存評価との差分照合・実行利用量集計のコードを用意し、合成データの関連44試験が通過した。既存1万分類の保持、実際の分類・別審査・利用条件・DB反映との対応、6軸と内容根拠付き非ジャンル特徴を確認する。利用量は最終監査で対応を確認した新規区間だけを集計し、分類・別審査の二重計上を避け、欠けた値は0で補わない。既存335評価は過去の保存ハッシュと一致することを確認済みで、元データを変更しない。実DBでの最終監査・差分評価・利用量集計は2万作品到達後に行う。

AI入力・表示・再配布・商用利用を別々に整理し、個人データの保存先、持ち出し・削除、無料運用範囲を[ToC候補](toc-candidate-v1.md)へ反映した。一般公開・商用提供はこの段階の完了条件に含めない。

実装の区切りで関連試験とコミット・pushを行う。確定した実装でUbuntu・WindowsのPython 3.14 CIを実行し、対象commitと検証結果を確認してPRを反映する。今回の計画説明だけを理由に、分類・取得・全試験を再実行しない。

直近の優先順位は、準備済み入力の供給を続けながら2万分類へ進むこと、並行作業の仕上げ、2万作品到達後の最終監査・HTTP確認・差分評価・文書更新・CI・PR反映の順とする。正常に動く分類を再起動したり、100作品ごとに全件監査や全CIを実行したりしない。最終区間は必要な新規採用数に合わせ、未使用資料から入力を固定する。

## その先
